Consult the stored digest on every path that serves a body

Every object has carried a sha256 of its bytes as stored since #109, and
three serve paths never looked at it, so a body mutated at rest could reach
a client with no end-to-end check at all.

- handlers.go skipped the check for cacheprog action keys on the theory that
  the client verifies outputid. It also ran after the self-heal, so a rotted
  body could be handed a fresh content address before anything questioned the
  bytes. The check now runs on every key, between the module-index guard and
  the self-heal.
- selfheal.go reconstructOutputID minted outputid = sha256(body) whenever the
  xattr was missing, which made the client's check tautological: it verified
  the body against a hash derived from that same body. It now refuses to mint
  a content address for a body that disagrees with its recorded digest.
- batch.go handleBatchGet streamed bodies with no digest check whatsoever, and
  buildPrefetchEntries feeds the same loop. This is the path the client
  actually uses. A member that fails is omitted (the client reads a missing
  member as a miss) and evicted.

storeddigest.go gains bodyMatchesStoredDigest, the map-free sibling
verifyStoredDigest delegates to, for the self-heal path that reads the digest
through an fd. The new "selfheal" and "batch_get" values on
s3_stored_digest_mismatch_total are label values on the existing CounterVec,
so no registration changes.
