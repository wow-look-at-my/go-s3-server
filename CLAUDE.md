# go-s3-server

Shared Go build cache server for go-toolchain. (Slated to be renamed **go-toolchain-cache**.)

It is **no longer S3-compatible**: the wire protocol is go-toolchain's native cache protocol (native `X-Cache-Meta-*` metadata headers and native plain-text errors), plus the custom `/_index` (GBCI v1 binary key index) and `/_batch/get` (tar transfer with prefetch) endpoints that replaced per-object S3 GETs. The only S3 remnant is a **deprecated** compatibility shim: legacy `X-Amz-Meta-*` request headers are still accepted (and still mirrored onto GET responses) so not-yet-upgraded clients keep working, but each use is logged once and counted in `s3_deprecated_requests_total`. The shim, the `s3_` metric/xattr prefixes, the `bucket` field, and the `go-s3-server` binary/module names are intentionally kept until the repository is renamed (see `deprecation.go`).

## Build & test

```
go-toolchain
```

Do NOT use `go build`, `go test`, or any bare `go` commands. Always use `go-toolchain` from the project root.

## Project layout

- `main.go` — CLI entry point (cobra). Serves in a goroutine and waits for `SIGINT`/`SIGTERM`, then calls `srv.BeginShutdown()` (flips `/_health` to 503) and `httpSrv.Shutdown(ctx)` with a `shutdownTimeout` (280s, kept under a typical container stop grace) so in-flight requests drain before exit instead of being cut off by a rolling-update `docker stop`
- `config.go` — JSON config loading and validation
- `auth.go` — HTTP Basic Auth; returns the authenticated username
- `auth_test.go` — Auth tests (including the "empty credential must not bypass auth" regression)
- `server.go` — HTTP router, auth gate, client-IP resolution, audit context, bucket dispatch. **Admission control**: a buffered `sem` channel sized to `max_concurrent_requests` bounds in-flight requests; when full, excess requests are shed with `503 + Retry-After` (never queued to OOM, which a proxy would report as `502`). `NewServer` defaults the limit so a directly-constructed `Config` is safe too. **Health/readiness**: an unauthenticated `GET /_health` probe is handled at the very top of `ServeHTTP` — before logging, metrics, auth, and admission control — returning `200`/`ok` normally and `503` once `BeginShutdown` sets the `shuttingDown` flag (so a health-checking proxy/LB in front, if any, takes the instance out of rotation during graceful shutdown — the drain itself relies on `Shutdown` closing the listener, not on the probe being watched).
- `server_test.go` — Health/readiness endpoint tests (`200` ok, `503` while draining, bypasses both the auth gate and admission control)
- `handlers.go` — object handlers (GetObject, PutObject, DeleteObject) plus `handleGetIndex` for the `/_index` endpoint, and `writeError` (native plain-text error responses: `<code>: <message>` body + `X-Cache-Error-Code` header, replacing the old S3 XML `<Error>`). Metadata travels in native `X-Cache-Meta-*` headers; PutObject also reads the deprecated `X-Amz-Meta-*` (filling only gaps native didn't set) and calls `noteDeprecatedS3Meta` when it sees one; GetObject emits **both** prefixes so old clients still read the outputid. **Self-heal**: when an indexed cacheprog object (`go-buildcache/v1<64-hex>`) has no `outputid` metadata, GetObject repairs it **in place** (`ensureOutputID` in `selfheal.go`) — reconstructs the outputid from the body (`outputID == sha256` of the decompressed body) and persists it via `storage.SetMeta`, then serves the object as a hit; the body, audit xattrs, and `_index` entry are all preserved (no eviction, no re-upload). A body that cannot be decompressed is reported as a clean `404` and left on disk for the normal eviction policy. Non-cacheprog keys are served as stored. GetObject and PutObject **stream** bodies (no whole-object buffering): GET `io.Copy`s from `storage.Open`; PUT streams via `storage.PutStream` wrapped in `http.MaxBytesReader(max_object_bytes)` (413 over the limit). PutObject **refuses Go module-index blobs**: it peeks a bounded but block-sized prefix of the upload (`io.ReadAll(io.LimitReader(body, indexPutPeekBytes))`, capped at `indexPutPeekBytes` = 1 MiB — the read **self-sizes** to the body's actual length rather than pre-allocating the full cap, so a typical small object allocates ~its own size, not 1 MiB; see the `modindex.go` bullet for why) and, if it decompresses to the `go index v` magic (`looksLikeGoModuleIndex` in `modindex.go`), accepts the request (`200`) but stores nothing — a mis-keyed module index poisons every consumer's build at package load and this shared Go build cache must never hold one (the client recomputes the index locally on the resulting miss); a non-index body is stitched back together via `io.MultiReader` and stored intact. GetObject **also refuses + evicts a module-index blob on READ** (`evictModuleIndexOnRead`, scoped to indexed cacheprog keys), running it **before** the outputid self-heal: it streams an `lz4.Reader` over the already-open file to recover the magic (`readIsModuleIndex`), and on a hit `storage.Delete`s the object (file + `/_index` entry) and returns `404` (a clean miss) instead of serving the poison; on a non-hit it `Seek(0)`s the file back so the served body is byte-for-byte unchanged. (The detection decodes the body's **full first lz4 block**, not a fixed 512-byte peek: the client packs each body into a single lz4 block and pierrec/lz4 needs the whole block to decode any output, so a real index — compressing to 521 B – ~36 KB, always > 512 — was never recognized under the old fixed peek, on either the read-evict or the PUT path.) This is the lazy, per-key self-heal that removes module-index poison **already on disk** (the PUT guard only blocks new ones) — see the `modindex.go` bullet — with **no `currentCacheVersion` bump**. PutObject writes audit xattrs (`content_length` is filled in by PutStream from the bytes actually streamed). DeleteObject is idempotent (204 even for a missing key) and is the surgical eviction lever for a poisoned cache entry — it removes the file and drops the key from the index (`Index.Remove`)
- `selfheal.go` — **in-place** self-healing for cache objects that lack `outputid` metadata (the GOCACHEPROG content address). Such objects are relics of earlier cache-data iterations, or had their xattrs stripped by a `data_dir` move: a client cannot verify the body without the outputid, so it discards the download and rebuilds (logging `missing outputid metadata`), yet the key stays advertised in `_index` so clients skip re-uploading it — a permanent forced miss. The fix is **repair, not eviction**: `outputID` is by definition `sha256` of the decompressed body, so `reconstructOutputID` lz4-decompresses the stored body (streamed straight into the hash — no whole-object buffering), recomputes the outputid, and persists it with `storage.SetMeta` (writes only that one xattr; body and audit xattrs untouched, `_index` entry kept). `missingOutputID` is the predicate; `ensureOutputID` orchestrates repair, mutates the in-memory `meta` to carry the reconstructed outputid, and bumps `s3_self_heal_repairs_total`. It is **scoped to indexed cacheprog keys** (`go-buildcache/v1<64-hex>`, via `extractActionHash`): those are the only keys advertised in `_index`, hence the only ones with the skip-re-upload permanent-miss problem. Any other key carries no cache-protocol contract and is served exactly as stored (so arbitrary/non-cache objects are never touched). Applied on **read** by `handlers.go` (single GET) and `batch.go` (requested-key loop and prefetch scan); the repair is one-time (the next read sees the outputid). A body that cannot be decompressed (unusable by the client regardless) is **left in place** — `ensureOutputID` returns false, the caller reports a clean miss, and the object is never deleted here (the normal age/size eviction policy handles it). This deliberately avoids an unauditable evict-and-re-upload churn pipeline. **Note** the module-index guard (`modindex.go`) runs at these same three read points (GET, batch requested-key loop, batch prefetch scan) — *before* this self-heal — but is the opposite policy: a module-index blob is *evicted* (refused + deleted, counted in `s3_module_index_evictions_total`), not repaired, since unlike an outputid-less object it can never be made usable
- `deprecation.go` — backward-compatibility shims for the retired S3 protocol. Defines the native (`x-cache-meta-`) and legacy (`x-amz-meta-`) metadata header prefixes and `noteDeprecatedS3Meta`, which logs a one-time `DEPRECATION:` warning (a CI run issues thousands of PUTs, so per-request logging would flood the log) and increments `s3_deprecated_requests_total{feature="amz_meta_header"}` on every legacy request
- `modindex.go` — `looksLikeGoModuleIndex`: detects a Go module index blob (optionally lz4-compressed) via the `go index v` magic. **The detection decodes the body's full first lz4 block, NOT a fixed-size compressed peek** — this is the load-bearing correctness point. The go-toolchain client packs each cached body into a **single lz4 block**, and pierrec/lz4's reader needs the **entire** block before it can decode any output. The guard used to peek only the first **512 compressed bytes** (`const indexPeekBytes = 512`) and lz4-decompress that prefix; but real module indexes compress to **521 B – ~36 KB** (always > 512), so the reader, handed a truncated 512-byte prefix, returned `n=0` (unexpected EOF), the magic was never seen, and **the poison was served on READ and stored on PUT** — both paths broken by the same truncation. (The old synthetic test passed only because its 2 KiB-of-`x` payload compressed to ~61 bytes, fitting in 512 — non-representative; verified against 5 real `s3.pazer.io` blobs that the old code returned false for all and the fix returns true for all.) The fix feeds the detector enough input to decode the first block: `indexMagicProbeBytes` (16) decompressed bytes are read, and the **read path streams an `lz4.Reader` straight off the open file** (it pulls exactly one block, however large), while the **PUT path reads a bounded but block-sized prefix** (capped at `indexPutPeekBytes`, 1 MiB — comfortably above the observed ~36 KB max and well below lz4's 4 MiB block ceiling). **The PUT peek self-sizes to the body** (`io.ReadAll(io.LimitReader(body, indexPutPeekBytes))`), allocating ~the body's actual size while `LimitReader` still caps the worst case at exactly `indexPutPeekBytes` — detection input is byte-identical to the old fixed cap. This replaced a `make([]byte, indexPutPeekBytes)` + `io.ReadFull` that pre-allocated the **full 1 MiB on every PUT** regardless of body size (a measured ~1 MB/op of pointless allocation churn): under a CI burst of ~7000 PUTs that thrashed GC and **saturated the admission-control `sem`**, shedding excess PUTs with `503` so nothing got stored/indexed — the next build then saw an empty `/_index` (`hits=0`) and blew the second-build time gate. The detection cap stays at 1 MiB (it bounds only the worst case now, not every PUT), so a real index's first block is always fully covered. Used to refuse a module index on **both** the write **and** read paths. **Write (PutObject):** the unscoped peek-and-refuse — any upload whose first block decodes to the magic is dropped (200, stored nothing) on any key; a non-index body is stitched back via `io.MultiReader` and stored intact (large bodies keep streaming). **Read (GET, batch get, prefetch):** `evictModuleIndexOnRead` (for a GET that holds the open file — detects via `readIsModuleIndex` streaming the `lz4.Reader` over the file, then `Seek(0)` rewinds so the non-index serve path is byte-for-byte unchanged) and `evictModuleIndexOnReadByKey` (the batch variant — opens-peeks-closes, since those paths Stat-then-stream and must decide before building the manifest) detect a module-index blob already on disk, **evict it** via `evictModuleIndex` → `storage.Delete` (drops the file and the `/_index` entry, the same lever DeleteObject uses), bump `s3_module_index_evictions_total`, and signal a miss so the client recomputes the index locally. Both read variants are **scoped to indexed cacheprog keys** (`go-buildcache/v1<64-hex>`, via `extractActionHash`) — exactly like the outputid self-heal — so an arbitrary/non-cache object is never inspected or touched. This is what removes already-stored poison: the PUT guard only blocks NEW indexes, while a blob uploaded before the guard existed (and surviving because the one-time v3 startup purge already ran) was otherwise served verbatim on every GET and re-advertised in `/_index` on every restart, with the client — which never re-uploads an index and has no remote DELETE — refusing and re-fetching it forever. The read guard sheds each poisoned key on its **first post-deploy fetch** (a lazy, incremental self-heal that needs no cache-wide `currentCacheVersion` bump and works regardless of client version). It runs orthogonally to, and **before**, the outputid self-heal: a module index carries an outputid, so `ensureOutputID` would pass it. A garbled `lz4` body that cannot be decompressed is treated as not-an-index (fail-open) on read, never an error that would fail the serve path. Pairs with the go-toolchain client, which also refuses to upload/serve/ingest index blobs.
- `index.go` — In-memory key index. Maintains an mtime-sorted list for `_batch/get` prefetch *and* a sorted slice of action-ID hashes that serializes to the GBCI v1 binary blob served at `GET /<bucket>/_index`. PUTs append to unsorted `pending` (hashes) and `pendingEntries` (mtime) buffers under a microsecond-scale mutex; both the hash sort+dedupe+serialize (deferred to the next `Blob()`) and the mtime merge+sort (deferred to the next `NearbyKeys`/`Remove` via `drainEntriesLocked`) are kept off the per-PUT path, so PUT is an O(1) append and writers don't convoy on a global sort.
- `storage.go` — Filesystem storage with two-level key sharding, cache version auto-purge, single-key `Delete` (used by DeleteObject), and single-key `SetMeta` (adds/overwrites specific metadata xattrs in place without touching the body or other xattrs — used by the outputid self-heal in `selfheal.go`). Bodies are streamed, never buffered: `PutStream` (io.Copy to a temp file, then write_once via streaming `filesEqual`), `Open` (returns an `*os.File` + meta for streaming reads), and `Stat` (meta/size only, no body) back the GET and batch paths. `Put([]byte,...)` is a thin wrapper over `PutStream` for in-memory callers and tests. Also holds **last-access tracking** for eviction: a sharded in-memory map (`accessShards`, 256 shards keyed by FNV-1a) updated by `recordAccess` on every `Open`/`Get`. Allocated only when `EnableAccessTracking` is called (eviction enabled), so the read hot path is free when eviction is off. Access time is kept *separate* from mtime — mtime stays the write time the prefetch system depends on.
- `eviction.go` — Background cache pruning. `Evict(maxAge, maxBytes, now)` runs one sweep: an **age pass** removes entries idle longer than `max_age` (idle = `now - max(mtime, lastAccess)`), then a **size pass** evicts least-recently-used survivors until total size is under `max_bytes`. Deletes files directly and rebuilds the index once at the end (not O(n) `Index.Remove` per victim → avoids O(n²)). `RunEvictionLoop` drives it on a ticker. Wired up in `main.go` only when `Eviction.Enabled()`; otherwise main logs a loud unbounded-growth warning.
- `eviction_test.go` — Eviction tests (age, access-time survival, size/LRU, index rebuild, access-record cleanup, Duration/config parsing)
- `storage_test.go` — Cache version / purge tests
- `storage_unix.go` / `storage_windows.go` — Platform-specific file locking, user metadata xattrs, and server audit xattrs
- `lock_windows.go` — Windows file locking via syscall
- `handlers_test.go` — Unit tests for handlers
- `modindex_test.go` — Tests for module-index detection and the PutObject refusal
- `.github/workflows/ci.yml` — CI pipeline (build, docker, s3-api-test, integration test)
- `.github/workflows/integration-test/` — Integration test harness (configs, test Go project)

## Conventions

- CLI parsing uses cobra. The single root command is in `main.go`.
- Error responses are native plain text (`writeError`: `<code>: <message>` body, `Content-Type: text/plain`, machine-readable code in the `X-Cache-Error-Code` header). Codes are snake_case (`not_found`, `unknown_bucket`, `access_denied`, `overloaded`, `conflict`, `too_large`, `method_not_allowed`, `invalid_request`, `internal_error`) — not S3 XML/error codes. The `/_index` endpoint serves a binary GBCI v1 blob (`application/octet-stream`) with a strong ETag (hex-encoded SHA-256 trailer); conditional GETs are handled by `http.ServeContent`.
- Object metadata is stored in filesystem extended attributes (xattr on Unix, ADS on Windows).
- Storage keys are sharded: `prefix/v1aabbccdd` → `prefix/v1/aa/bbccdd`.
- `write_once` config is an object: `{"action": "allow"|"deny", "notification": "never"|"always"|"content_differs"}`. Defaults: `action=allow`, `notification=never`.
- HTTP Basic Auth with `username`/`password` credentials. To run without auth, set `disable_auth: true` (and omit `credentials`). The old empty-string convention for disabling auth has been removed — empty strings in a credential entry are now a config error.
- `credentials` config is required unless `disable_auth: true`. Each entry needs both `username` and `password` set to non-empty values.
- String config values support env var references: `{"type": "envvar", "name": "VAR_NAME"}` resolves to `os.Getenv("VAR_NAME")` at load time. Used via the `ConfigString` type. An env var that resolves to `""` is rejected the same as a literal empty string, so an unset env var cannot silently disable auth.
- Every `PutObject` persists audit metadata as extended attributes on the stored file: `user.s3audit.uploader`, `user.s3audit.uploaded_at`, `user.s3audit.client_ip`, `user.s3audit.user_agent`, `user.s3audit.content_length`. Namespace `user.s3audit.*` is separate from user-supplied metadata headers (native `X-Cache-Meta-*`, or the deprecated `X-Amz-Meta-*`), which are stored as `user.s3.*`, so user metadata cannot spoof audit fields. (The `user.s3*` xattr prefixes are kept until the repo rename.) On Windows, audit is a JSON sidecar at `<path>.audit`.
- Client IP is resolved via `CF-Connecting-IP` → `X-Real-IP` → first entry of `X-Forwarded-For` → `r.RemoteAddr`. These proxy headers are trusted unconditionally; deploy only behind a trusted reverse proxy.
- Cache version: `storage.go` stamps the `data_dir` with a `.cache_version` file. `currentCacheVersion` is a constant in `storage.go`. On startup, if the stored version (or 1, if the marker is missing) differs from current, every entry in `data_dir` is removed before serving. Bump `currentCacheVersion` to force operators to rebuild the cache after a change that should invalidate prior contents. Version 3 purges caches that may hold poisoned Go module-index objects (a mis-keyed index breaks consumers' builds with `package runtime is not in std` / `corrupt index`); the purge repairs every client at once, while the PutObject refusal above keeps new ones out.
- `eviction` config is an object: `{"max_age": "720h", "max_bytes": 0, "interval": "72h"}`. `interval` defaults to 3 days (`defaultEvictionInterval`) — infrequent on purpose, since a 30-day age window gains nothing from frequent sweeps; shorten it only for a tight `max_bytes`. `max_age`/`interval` are Go duration strings (or seconds as a number) parsed by the `Duration` type in `config.go`; `max_bytes` is an int. `max_age` is a `*Duration` so an absent field takes the default (`defaultEvictionMaxAge`, 30 days) while an explicit `"0"` disables it — `max_bytes` defaults to `0` (off). Eviction is **on by default**; both off → unbounded growth + a startup warning. Eviction is driven by *last use* (`max(mtime, lastAccess)`), never by rewriting mtime, so the prefetch grouping that keys on mtime is unaffected. Metrics: `s3_evictions_total`, `s3_evicted_bytes_total`, `s3_cache_bytes`. Separately, the on-read self-heal (see `selfheal.go`) counts outputid-less relics it repairs **in place** in `s3_self_heal_repairs_total`, and the on-read module-index guard (see `modindex.go`) counts already-stored module-index blobs it **evicts** on a read path in `s3_module_index_evictions_total`.
