# go-s3-server

Shared Go build cache server for go-toolchain. (Slated to be renamed **go-toolchain-cache**.)

This server is **no longer S3-compatible**. The wire protocol is go-toolchain's native cache protocol. It carries native `X-Cache-Meta-*` metadata headers and native plain-text errors. Custom endpoints replaced the per-object S3 GETs and PUTs. `/_index` serves the GBCI v1 binary key index. `/_batch/get` transfers a tar and prefetches nearby keys. `/_batch/put` uploads many objects in one tar. The only S3 remnant is a **deprecated** compatibility shim. It still accepts legacy `X-Amz-Meta-*` request headers and still mirrors them onto GET responses. A client that is not yet upgraded therefore keeps working. Each use is logged once and counted in `s3_deprecated_requests_total`. These names stay until the repository is renamed. The list is the shim, the `s3_` metric and xattr prefixes, the `bucket` field, and the `go-s3-server` binary and module names. See `deprecation.go`.

## Build & test

```
go-toolchain
```

Do NOT use `go build`, `go test`, or any bare `go` commands. Always use `go-toolchain` from the project root.

## Project layout

- `cacheclient/` — **the client side of this server's wire protocol, as its own Go module** (`github.com/wow-look-at-my/go-s3-server/cacheclient`): single GET/PUT, `/_index`, `/_batch/get`, `/_batch/put`, lz4 framing, and the three read guards (outputid hash, build-id action, module index). Protocol and server change together in one repo, so a header or endpoint cannot drift between them. Its own `go.mod` keeps the dependency list to lz4 and `go-containers/set` — the server's cobra/prometheus tree stays out — because a consumer vendors this into a tree that will not take them. Diagnostics go to a `Logger` the consumer installs (silence by default: a caller whose stdout is a protocol channel must not have stderr written for it). It carries NO tracing: OpenTelemetry cannot be reimplemented by hand here, and instrumentation waits on gosmopolitan compiler integration. Its consumer is gosmopolitan's `cmd/go`, which calls the cache in process; go-toolchain's `cacheprog` subcommand, which spawned it as a `GOCACHEPROG` subprocess, has been deleted.
- `main.go` — CLI entry point (cobra). Serves in a goroutine and waits for `SIGINT`/`SIGTERM`, then calls `srv.BeginShutdown()` (flips `/_health` to 503) and `httpSrv.Shutdown(ctx)` with a `shutdownTimeout` (280s, kept under a typical container stop grace) so in-flight requests drain before exit instead of being cut off by a rolling-update `docker stop`
- `config.go` — JSON config loading and validation
- `auth.go` — HTTP Basic Auth; returns the authenticated username
- `auth_test.go` — Auth tests (including the "empty credential must not bypass auth" regression)
- `server.go` — HTTP router, auth gate, client-IP resolution, audit context, bucket dispatch. Routes: `GET /_index`, `PUT /_index`, `GET|POST /_batch/get` (POST is the semantically sound method for the body-carrying batch lookup; GET stays for older clients), `PUT /_batch/put` (tar bulk upload), `GET`/`HEAD`/`PUT`/`DELETE` on object keys. **Admission control**: a buffered `sem` channel sized to `max_concurrent_requests` bounds in-flight requests; when full, excess requests are shed with `503 + Retry-After` (never queued to OOM, which a proxy would report as `502`). `NewServer` defaults the limit so a directly-constructed `Config` is safe too. **Health/readiness**: an unauthenticated `GET /_health` probe is handled at the very top of `ServeHTTP` — before logging, metrics, auth, and admission control — returning `200`/`ok` normally and `503` once `BeginShutdown` sets the `shuttingDown` flag (so a health-checking proxy/LB in front, if any, takes the instance out of rotation during graceful shutdown — the drain itself relies on `Shutdown` closing the listener, not on the probe being watched).

- **Update-check endpoints** — `GET /.well-known/docker-updater/{health,pre-update}` answer beside `/_health` at the top of
  `ServeHTTP`, clearing the same three gates (auth, admission control, the access log). Both are aliases of the drain flag, not

- `server_test.go` — Health/readiness endpoint tests (`200` ok, `503` while draining, bypasses both the auth gate and admission control)
- `handlers.go` — object handlers (GetObject, PutObject, DeleteObject) plus `handleGetIndex` and `handlePutIndex` for the `/_index` endpoint, and `writeError` (native plain-text error responses: `<code>: <message>` body + `X-Cache-Error-Code` header, replacing the old S3 XML `<Error>`). Metadata travels in native `X-Cache-Meta-*` headers; PutObject also reads the deprecated `X-Amz-Meta-*` (filling only gaps native didn't set) and calls `noteDeprecatedS3Meta` when it sees one; GetObject emits **both** prefixes so old clients still read the outputid. **Self-heal**: when an indexed cacheprog object (`go-buildcache/v1<64-hex>`) has no `outputid` metadata, GetObject repairs it **in place** (`ensureOutputID` in `selfheal.go`) — reconstructs the outputid from the body (`outputID == sha256` of the decompressed body) and persists it fd-based via `setMetadataFd` (see `selfheal.go`), then serves the object as a hit; the body, audit xattrs, and `_index` entry are all preserved (no eviction, no re-upload). A body that cannot be decompressed is reported as a clean `404`, counted, DE-advertised from `/_index`, and left on disk for the normal eviction policy. Non-cacheprog keys are served as stored. GetObject and PutObject **stream** bodies (no whole-object buffering): GET `io.Copy`s from `storage.Open`; PUT streams via `storage.PutStream` wrapped in `http.MaxBytesReader(max_object_bytes)` (413 over the limit). PutObject **refuses Go module-index blobs**: it peeks a bounded but block-sized prefix of the upload (`io.ReadAll(io.LimitReader(body, indexPutPeekBytes))`, capped at `indexPutPeekBytes` = 1 MiB — the read **self-sizes** to the body's actual length rather than pre-allocating the full cap, so a typical small object allocates ~its own size, not 1 MiB; see the `modindex.go` bullet for why) and, if it decompresses to the `go index v` magic (`looksLikeGoModuleIndex` in `modindex.go`), accepts the request (`200`) but stores nothing — a mis-keyed module index poisons every consumer's build at package load and this shared Go build cache must never hold one (the client recomputes the index locally on the resulting miss); a non-index body is stitched back together via `io.MultiReader` and stored intact. GetObject **also refuses + evicts a module-index blob on READ** (`evictModuleIndexOnRead`, scoped to indexed cacheprog keys), running it **before** the outputid self-heal: it streams an `lz4.Reader` over the already-open file to recover the magic (`readIsModuleIndex`), and on a hit `storage.Delete`s the object (file + `/_index` entry) and returns `404` (a clean miss) instead of serving the poison; on a non-hit it `Seek(0)`s the file back so the served body is byte-for-byte unchanged. (The detection decodes the body's **full first lz4 block**, not a fixed 512-byte peek: the client packs each body into a single lz4 block and pierrec/lz4 needs the whole block to decode any output, so a real index — compressing to 521 B – ~36 KB, always > 512 — was never recognized under the old fixed peek, on either the read-evict or the PUT path.) This is the lazy, per-key self-heal that removes module-index poison **already on disk** (the PUT guard only blocks new ones) — see the `modindex.go` bullet — with **no `currentCacheVersion` bump**. PutObject writes audit xattrs (`content_length` is filled in by PutStream from the bytes actually streamed). The module-index refusal is **counted and logged** (`s3_put_refusals_total{reason="module_index"}` + a per-refusal log line naming the key) — the counter moving during CI activity is the guard's liveness proof, closing the blind spot that hid the 512-byte-peek bug; a refused PUT never reaches `Index.Put` (that call sits after PutStream's rename), so a refused key is never advertised. Every single-object GET lands in `s3_get_requests_total{outcome}`: `hit`, `miss_not_found`, `miss_advertised_unservable` (404 on a key whose action hash `Index.Contains` still reports advertised — the index/store-divergence signature, should be ~0), `miss_module_index_evicted`, `miss_peek_error` (guard could not inspect/rewind), `miss_selfheal_failed`. The GET body copy keeps `f` as the direct `io.Copy` source (preserving the ReadFrom/sendfile path) and logs disk-side copy failures (`*fs.PathError`) — client disconnects stay unlogged. `handleHeadObject` answers `HEAD /{bucket}/{key}`: Stat-based, the exact GET header surface (both meta prefixes + Content-Length + Last-Modified), no body, no guard probe, no self-heal, no last-access stamp. DeleteObject is idempotent (204 even for a missing key) and is the surgical eviction lever for a poisoned cache entry — it removes the file and drops the key from the index (`Index.Remove`). **Shared store path**: `storeOneObject(storage, key, body, meta, audit) (status, err)` factors out the module-index peek-refuse (including the refusal counter + per-refusal log, which therefore fire for batch-put members too) + write_once + `PutStream` (audit + index append) logic so both `handlePutObject` (one object) and `handleBatchPut` (many) call it and cannot drift; it returns a `storeStatus*` (`stored`/`dropped`/`conflict`/`error`) the caller maps to an HTTP status (single PUT) or records per object (batch). `handlePutObject` maps `dropped`→200/no-store (module index), `conflict`→409, a wrapped `*http.MaxBytesError`→413
- `handlers.go` — the object handlers (`GetObject`, `PutObject`, `HeadObject`, `DeleteObject`), `handleGetIndex` for `/_index`, `writeError` (native plain-text errors: `<code>: <message>` body + `X-Cache-Error-Code`), and `storeOneObject`, the shared store path both single PUT and `/_batch/put` go through so they cannot drift. Bodies stream in both directions — nothing whole-object is ever buffered. Every read applies the module-index guard and then the outputid self-heal; every single-object GET lands in `s3_get_requests_total{outcome}`. Depth: `docs/object-handlers.md`
- `cleanmemo.go` — the **known-clean key memo**: a sharded (256-way on the action hash's first byte) in-memory set of indexed cacheprog keys whose stored body already passed the read-path module-index probe. Both read guards consult it and skip the open+lz4-decode on a hit, so warm keys pay the probe once, not per GET/batch/prefetch. Invalidated wherever the body can change or vanish: overwrite PUT (`PutStream` after rename), `Delete`, and eviction (`evictOne`) — all via `Storage.forgetClean`. Bounded at 1M entries (`maxCleanMemoEntries`); past the bound it clears wholesale and repopulates by re-probing. Nil-safe accessors keep directly-constructed `Storage` values working; the memo is a probe-skip optimization, not the safety boundary (the PUT guard remains the gate that keeps new indexes out).
- `lrucache.go` — the **byte-bounded sharded LRU** every in-memory cache is built on: a budget in bytes, least-recently-used eviction to stay inside it, and `SetBudget` to change the bound at runtime (evicting immediately). 64 shards, each holding an equal slice of the budget, so an insert evicts only within its own shard and the hot path stays lock-local. An entry larger than its shard's whole budget is still held (a cache that refuses to hold anything is a permanent miss), so the bound is "budget + at most one entry per shard"
- `memlimit.go` — **memory awareness**: the process ceiling (`debug.SetMemoryLimit(-1)` — GOMEMLIMIT or go-toolchain's injected cgroup guard — else the cgroup files, else 0 = unknown) sizes each cache's budget, and `memController` samples every 250ms and moves ONE number: the scale applied to those budgets. `resolveMemoryBudget` runs from `run()`, NOT a package-level initializer: go-toolchain's injected `gomemlimit_gen.go` sets `GOMEMLIMIT` to 0.9× the cgroup limit from an `init()`, and package variables initialize before any `init()`, so detecting early reported the raw container limit — a ceiling nothing enforced. The server never installs a limit of its own. Above 85% in use it halves the scale (evicting) and returns memory to the OS; below 65% it grows back by 25%; at the floor (1/32) it stops and logs that the container needs more memory. **It cannot touch request handling** — a cache server that refuses to serve is useless, since every client it turns away rebuilds anyway. An unknown budget disables the controller and leaves fixed defaults. Metrics: `s3_memory_{limit,in_use}_bytes`, `s3_memory_shrinks_total`, `s3_cache_memory_bytes{cache}`, `s3_cache_memory_budget_bytes{cache}`. Depth: `docs/memory-limits.md`
- `metacache.go` — the **per-key metadata cache**: an object's user metadata against the mtime+size it was read under, so a warm `Stat`/`Open` skips the `listxattr` + per-attribute `getxattr` (~42us per key, paid 128 times per batch). Self-validating: a hit is served only when the fresh stat matches, and an overwrite is a new inode, so stale metadata cannot be served. An xattr stamped onto a LIVE inode (the outputid self-heal) is the one case the stat cannot see, so it drops the entry explicitly (`forgetMeta`) — as do `Delete`, `SetMeta`, and eviction. Bounded (64k, clears wholesale); `s3_meta_cache_hits_total`/`_misses_total`. Depth: `docs/hot-path-cpu.md`
- `cacheversion.go` — the `data_dir` format version (`currentCacheVersion`), its startup purge, and the `.tmp-*` orphan sweep. Split out of `storage.go`; both run once, before serving, under the data_dir's exclusive lock
- `selfheal.go` — **in-place** self-healing for cache objects that lack `outputid` metadata (the GOCACHEPROG content address). Such objects are relics of earlier cache-data iterations, or had their xattrs stripped by a `data_dir` move: a client cannot verify the body without the outputid, so it discards the download and rebuilds (logging `missing outputid metadata`), yet the key stays advertised in `_index` so clients skip re-uploading it — a permanent forced miss. The fix is **repair, not eviction**: `outputID` is by definition `sha256` of the decompressed body, so `reconstructOutputID` lz4-decompresses the stored body (streamed straight into the hash — no whole-object buffering), recomputes the outputid, and persists it **through the same file descriptor it hashed** (`setMetadataFd` → `unix.Fsetxattr`; writes only that one xattr; body and audit xattrs untouched, `_index` entry kept). Fd-based stamping fixes the stale-stamp race: the old path-based `storage.SetMeta` could land the OLD inode's hash on a body a concurrent overwrite PUT had just renamed into place, leaving `outputid != sha256(body)` permanently (every client discards the download yet never re-uploads). On the GET path the repair hashes the handler's own serve handle and rewinds it (a failed rewind fails the repair rather than serving a consumed fd), so the emitted outputid always describes the exact bytes streamed; the batch paths pass nil and the repair opens/stamps a private raw handle (`openRaw`, no access-record/op-metric). A pre-existing outputid found DISAGREEING with the just-computed body hash is counted (`s3_outputid_mismatch_total`) and corrected in place. `missingOutputID` is the predicate; `ensureOutputID(storage, key, meta, f)` orchestrates repair, mutates the in-memory `meta` to carry the reconstructed outputid, and bumps `s3_self_heal_repairs_total`. It is **scoped to indexed cacheprog keys** (`go-buildcache/v1<64-hex>`, via `extractActionHash`): those are the only keys advertised in `_index`, hence the only ones with the skip-re-upload permanent-miss problem. Any other key carries no cache-protocol contract and is served exactly as stored (so arbitrary/non-cache objects are never touched). Applied on **read** by `handlers.go` (single GET) and `batch.go` (requested-key loop and prefetch scan); the repair is one-time (the next read sees the outputid). A body that cannot be decompressed (unusable by the client regardless) is **left on disk but DE-ADVERTISED** — `ensureOutputID` returns false, counts `s3_self_heal_failures_total`, drops the key from `/_index` (`Index.Remove`; the file stays for forensics and the eviction policy), and the caller reports a clean miss. De-advertising matters: clients skip re-uploading indexed keys, so an unrepairable-but-advertised key was a permanent forced miss; unindexed, the next consumer re-uploads a good body and heals it (a startup/sweep-end rebuild re-advertises it from disk until then — bounded churn, strictly better than the wedge). Deleting the body here is still deliberately avoided (no unauditable evict-and-re-upload churn pipeline). **Note** the module-index guard (`modindex.go`) runs at these same three read points (GET, batch requested-key loop, batch prefetch scan) — *before* this self-heal — but is the opposite policy: a module-index blob is *evicted* (refused + deleted, counted in `s3_module_index_evictions_total`), not repaired, since unlike an outputid-less object it can never be made usable
- `deprecation.go` — backward-compatibility shims for the retired S3 protocol. Defines the native (`x-cache-meta-`) and legacy (`x-amz-meta-`) metadata header prefixes and `noteDeprecatedS3Meta`, which logs a one-time `DEPRECATION:` warning (a CI run issues thousands of PUTs, so per-request logging would flood the log) and increments `s3_deprecated_requests_total{feature="amz_meta_header"}` on every legacy request
- `modindex.go` — `looksLikeGoModuleIndex`: detects a Go module index blob (optionally lz4-compressed) via the `go index v` magic. **The detection decodes the body's full first lz4 block, NOT a fixed-size compressed peek** — this is the load-bearing correctness point. The go-toolchain client packs each cached body into a **single lz4 block**, and pierrec/lz4's reader needs the **entire** block before it can decode any output. The guard used to peek only the first **512 compressed bytes** (`const indexPeekBytes = 512`) and lz4-decompress that prefix; but real module indexes compress to **521 B – ~36 KB** (always > 512), so the reader, handed a truncated 512-byte prefix, returned `n=0` (unexpected EOF), the magic was never seen, and **the poison was served on READ and stored on PUT** — both paths broken by the same truncation. (The old synthetic test passed only because its 2 KiB-of-`x` payload compressed to ~61 bytes, fitting in 512 — non-representative; verified against 5 real `s3.pazer.io` blobs that the old code returned false for all and the fix returns true for all.) The fix feeds the detector enough input to decode the first block: `indexMagicProbeBytes` (16) decompressed bytes are read, and the **read path streams an `lz4.Reader` straight off the open file** (it pulls exactly one block, however large), while the **PUT path reads a bounded but block-sized prefix** (capped at `indexPutPeekBytes`, 1 MiB — comfortably above the observed ~36 KB max and well below lz4's 4 MiB block ceiling). **The PUT peek self-sizes to the body** (`io.ReadAll(io.LimitReader(body, indexPutPeekBytes))`), allocating ~the body's actual size while `LimitReader` still caps the worst case at exactly `indexPutPeekBytes` — detection input is byte-identical to the old fixed cap. This replaced a `make([]byte, indexPutPeekBytes)` + `io.ReadFull` that pre-allocated the **full 1 MiB on every PUT** regardless of body size (a measured ~1 MB/op of pointless allocation churn): under a CI burst of ~7000 PUTs that thrashed GC and **saturated the admission-control `sem`**, shedding excess PUTs with `503` so nothing got stored/indexed — the next build then saw an empty `/_index` (`hits=0`) and blew the second-build time gate. The detection cap stays at 1 MiB (it bounds only the worst case now, not every PUT), so a real index's first block is always fully covered. Used to refuse a module index on **both** the write **and** read paths. **Write (PutObject):** the unscoped peek-and-refuse — any upload whose first block decodes to the magic is dropped (200, stored nothing) on any key; a non-index body is stitched back via `io.MultiReader` and stored intact (large bodies keep streaming). **Read (GET, batch get, prefetch):** `evictModuleIndexOnRead` (for a GET that holds the open file — detects via `readIsModuleIndex` streaming the `lz4.Reader` over the file, then `Seek(0)` rewinds so the non-index serve path is byte-for-byte unchanged) and `evictModuleIndexOnReadByKey` (the batch variant — opens-peeks-closes, since those paths Stat-then-stream and must decide before building the manifest) detect a module-index blob already on disk, **evict it** via `evictModuleIndex` → `storage.Delete` (drops the file and the `/_index` entry, the same lever DeleteObject uses), bump `s3_module_index_evictions_total`, and signal a miss so the client recomputes the index locally. Both read variants are **scoped to indexed cacheprog keys** (`go-buildcache/v1<64-hex>`, via `extractActionHash`) — exactly like the outputid self-heal — so an arbitrary/non-cache object is never inspected or touched. This is what removes already-stored poison: the PUT guard only blocks NEW indexes, while a blob uploaded before the guard existed (and surviving because the one-time v3 startup purge already ran) was otherwise served verbatim on every GET and re-advertised in `/_index` on every restart, with the client — which never re-uploads an index and has no remote DELETE — refusing and re-fetching it forever. The read guard sheds each poisoned key on its **first post-deploy fetch** (a lazy, incremental self-heal that needs no cache-wide `currentCacheVersion` bump and works regardless of client version). It runs orthogonally to, and **before**, the outputid self-heal: a module index carries an outputid, so `ensureOutputID` would pass it. A garbled-but-READABLE `lz4` body is treated as not-an-index (fail-open) on read, never an error that would fail the serve path; a genuine source I/O error, however, is now distinguished (`errTrackingReader` wraps the source) and surfaces as a refused serve — `guardPeekError` → `miss_peek_error` — instead of fail-opening into a 200 that dies mid-copy. The GET-path guard returns a three-way `readGuardVerdict` (`guardServe`/`guardEvicted`/`guardPeekError`) so the distinct miss reasons are counted. **Perf**: every probe calls `zr.Reset(nil)` after the 16-byte magic read, returning pierrec/lz4's two pooled 4 MiB buffers — an abandoned reader never returns them, and before this fix every peek churned ~8.4 MiB of allocation on every GET/PUT/batch/prefetch inspection (BenchmarkPutObjectPeek: 8.49 MB/op → ~133 KB/op). Repeat probes are skipped entirely via the known-clean memo (`cleanmemo.go`), and the batch peek opens through `storage.openRaw` so it neither double-counts the "get" storage op nor stamps last-access onto candidates that are never served. Pairs with the go-toolchain client, which also refuses to upload/serve/ingest index blobs.
- `index.go` — In-memory key index. Maintains an mtime-sorted list for `_batch/get` prefetch *and* a sorted slice of action-ID hashes that serializes to the GBCI v1 binary blob served at `GET /<bucket>/_index`. PUTs append to unsorted `pending` (hashes) and `pendingEntries` (mtime) buffers under a microsecond-scale mutex; both the hash sort+dedupe+serialize (deferred to the next `Blob()`) and the mtime merge+sort (deferred to the next `NearbyKeys`/`Remove` via `drainEntriesLocked`) are kept off the per-PUT path, so PUT is an O(1) append and writers don't convoy on a global sort. **Rebuild merges, never clobbers**: `rebuild` walks the FS then calls `applyRebuild`, which replaces the master lists but PRESERVES the pending buffers (walked hashes are prepended to surviving `pending`; `pendingEntries` drains normally later) — the old rebuild nil'd both buffers, silently dropping every PUT that completed during the multi-second walk from `/_index` until the next rebuild. **`RemoveKeys`** batch-drops a victim set (entries + hashes + pending) in one O(n+v) filter pass — the eviction sweeper calls it BEFORE unlinking any file so a key is never advertised-but-deleted mid-sweep. **`Contains`** is the O(log n)+O(pending) membership probe behind the `miss_advertised_unservable` GET outcome. **ETag purity**: the serialized `generation` header field is CONTENT-DERIVED (first 8 bytes of the hash body's digest), not a serialization counter, so the blob — and the ETag — is a pure function of the advertised key set: duplicate-only PUT traffic and restarts reserialize byte-identically and clients keep getting 304s (the client never reads the field; it validates magic/version/hashSize/length/trailer only). Size gauges (`s3_index_entries`/`s3_index_hashes`/`s3_index_pending_hashes`) update at every mutation; full rebuilds are timed in `s3_index_rebuild_duration_seconds`. `PUT /_index` accepts a client-uploaded GBCI blob and merges its hashes into the pending queue via `Index.Merge`.
- `modindex.go` + `lz4head.go` — the **module-index guard**: this shared cache must never hold a Go module index (it carries no build id, does not bind to its action key, and a mis-keyed one breaks every consumer's build at package load). Refused on PUT, and evicted on read (GET, batch, prefetch) for indexed cacheprog keys. The verdict comes from an lz4 frame-header walk that reads the first literal run instead of decoding a block (183ns, no allocation, any object size), falling back to a real decode for any frame shape it cannot fully parse. Depth, invariants, and history: `docs/module-index-guard.md`
- `index.go` — In-memory key index. Maintains an mtime-sorted list of `indexEntry` (a `compactKey` + mtime, so a million-key index carries no per-key allocation) for `_batch/get` prefetch *and* a sorted slice of action-ID hashes that serializes to the GBCI v1 binary blob served at `GET /<bucket>/_index`. PUTs append to unsorted `pending` (hashes) and `pendingEntries` (mtime) buffers under a microsecond-scale mutex; both the hash sort+dedupe+serialize (deferred to the next `Blob()`) and the mtime merge+sort (deferred to the next `NearbyKeys`/`Remove` via `drainEntriesLocked`) are kept off the per-PUT path, so PUT is an O(1) append and writers don't convoy on a global sort. A drain releases a pending buffer grown past `maxRetainedPending` instead of holding a rebuild-sized array forever. **Rebuild merges, never clobbers**: `rebuild` streams `Storage.Walk` into an `indexBuild` (sorted+deduped off-lock) and `applyRebuild` installs it while PRESERVING the pending buffers — the old rebuild nil'd both, silently dropping every PUT that completed during the multi-second walk from `/_index` until the next rebuild. **`RemoveKeys`** batch-drops a victim set (entries + hashes + pending) in one O(n+v) filter pass — the eviction sweeper calls it BEFORE unlinking any file so a key is never advertised-but-deleted mid-sweep. **`Contains`** is the O(log n)+O(pending) membership probe behind the `miss_advertised_unservable` GET outcome. **ETag purity**: the serialized `generation` header field is CONTENT-DERIVED (first 8 bytes of the hash body's digest), not a serialization counter, so the blob — and the ETag — is a pure function of the advertised key set: duplicate-only PUT traffic and restarts reserialize byte-identically and clients keep getting 304s (the client never reads the field; it validates magic/version/hashSize/length/trailer only). Size gauges (`s3_index_entries`/`s3_index_hashes`/`s3_index_pending_hashes`) update at every mutation; full rebuilds are timed in `s3_index_rebuild_duration_seconds`.
- `batch.go` — the tar batch endpoints. **`handleBatchGet`** — the `/_batch/get` endpoint (GET or POST; POST is preferred — the request carries a JSON body and GET-with-a-body is proxy-hostile). Phase 1 stats requested keys (module-index guard + self-heal gate each), phase 2 streams found bodies into a tar after a `manifest.json`. Prefetch is ordered for cheapness: `NearbyKeys` candidates are **tracker-suppressed FIRST** (`prefetchTracker.filterKeys` — a map lookup per key), only survivors pay the stat/guard/heal work (`buildPrefetchEntries`), and only keys actually included in the response are recorded as sent (`tracker.record`), so a candidate dropped by the guard stays eligible later. The guard peek and self-heal use raw opens (no "get" op metric, no last-access stamp), so a batch of N served keys performs exactly N counted gets and prefetch candidates never gain LRU lifetime they didn't earn. Volume lands in `s3_batch_requests_total` + `s3_batch_keys_total{kind=requested|found|prefetched|suppressed|streamed}` as well as the log line. **`handleBatchPut`** (PUT `/_batch/put`, Content-Type `application/x-tar`) is the bulk-upload counterpart: the go-toolchain client issues one HTTP PUT per cached object and a CI build produces thousands, each taking an admission-control `sem` slot and saturating the server (shedding uploads with 503); `/_batch/put` accepts a tar of many objects in ONE request holding ONE sem slot. The tar is `manifest.json` (FIRST member: `{"entries":[{"key":...,"metadata":{name→value, keyed by lowercased meta name without the `X-Cache-Meta-` prefix}}]}`) then one `data/<key>` member per entry in manifest order; each member is stored via the shared `storeOneObject`, and the response is JSON `{"results":[{"key":...,"status":"stored|dropped|conflict|error","message":...}]}`, one per manifest key. A per-member store failure is recorded as `error` and does NOT abort the batch. The whole batch body is bounded by `http.MaxBytesReader` at `maxBatchKeys × max_object_bytes` (413 over), entries capped at `maxBatchKeys` (413 over), each member bounded to `max_object_bytes`; a malformed tar / missing-or-late `manifest.json` / a data member with no manifest entry (or a manifest entry with no data member) / a duplicate key → whole-request 400 `invalid_request`. The request-level audit (uploader, IP, UA, timestamp) is shared across members (cloned per member via `cloneAudit` because `PutStream` writes per-member `content_length`). Module-index members are refused inside the shared `storeOneObject` (recorded as `dropped`, counted in `s3_put_refusals_total` exactly like single-PUT refusals); per-batch volume is visible via the `route="BatchPut"` HTTP metrics and the `batch put: entries=… stored=… dropped=… conflict=… error=…` log line
- `storage.go` — Filesystem storage with two-level key sharding, single-key `Delete` (used by DeleteObject), and single-key `SetMeta` (adds/overwrites specific metadata xattrs in place without touching the body or other xattrs — used by the outputid self-heal in `selfheal.go`). Bodies are streamed, never buffered: `PutStream` (io.Copy to a temp file, then write_once via streaming `filesEqual`), `Open` (returns an `*os.File` + meta for streaming reads), and `Stat` (meta/size only, no body) back the GET and batch paths. `Put([]byte,...)` is a thin wrapper over `PutStream` for in-memory callers and tests. `openRaw` opens a body with NO storage-op metric and NO last-access recording — for internal peeks (module-index guard, self-heal hashing) that are not client-visible serves. `OpenBody` is `Open` minus the metadata read (open + size + last-access + the same `get` op), used by the batch streaming phase, whose manifest already carries the metadata. **Durability**: `PutStream` fsyncs temp files >= `fsyncThresholdBytes` (8 MiB) before the rename (small objects skip it; the client hash-verifies every download), and `NewStorage` sweeps orphaned `.tmp-*` files at startup (they are invisible to `Walk`/eviction and otherwise leak disk forever; safe because the exclusive flock guarantees no in-flight writer). PutStream also invalidates the known-clean memo (`forgetClean`) after every rename, and `finalizeSidecars` moves the Windows metadata sidecars along with the body (no-op on unix). `Storage` also carries `cleanKeys` (the known-clean memo, see `cleanmemo.go`) and `metaCache` (see `metacache.go`). `Walk(fn)` is the metadata-only enumeration (key, size, mtime, atime) both the index rebuild and the eviction sweep are built on — a callback, not a slice, because materializing a million keys as strings was this process's largest allocation. Also holds **last-access tracking** for eviction: a sharded in-memory map (`accessShards`, 256 shards, keyed by `compactKey`) updated by `recordAccess` on every `Open`/`Get`, allocated only when `EnableAccessTracking` is called — which `main.go` does only when the data_dir does not record file access times, since the filesystem's own atime is durable and free. Access time is kept *separate* from mtime — mtime stays the write time the prefetch system depends on.
- `eviction.go` — Background cache pruning: an **LRU bounded by `max_bytes`**, with `max_age` as an off-by-default TTL. `Evict(maxAge, maxBytes, now)` walks the data_dir twice and never lists it: walk 1 measures total bytes plus a bounded last-use histogram, from which it derives ONE cutoff (`max(ageCutoff, sizeCutoff)`); walk 2 deletes everything below the cutoff in batches of 65k, each **de-advertised from `/_index` before its files are unlinked**, then rebuilds the index once as a true-up. `evictOne(key, expectMtime)` re-stats before deleting (the overwrite TOCTOU) and drops the access record, known-clean memo and Windows sidecars. Last use is `max(mtime, atime, in-memory record)`; the in-memory `accessShards` map exists only when the data_dir does not record access times. `RunEvictionLoop` schedules from the `.last_sweep` marker (sweep at startup when a full interval has passed, else wait out the remainder) and refreshes `s3_cache_bytes` every 15 min. Wired up in `main.go` only when `Eviction.Enabled()`; otherwise main logs a loud unbounded-growth warning. Depth: `docs/eviction.md`
- `atime.go` (+ `atime_linux.go` / `atime_windows.go` / `atime_other.go`) — durable last-use. `fileAccessTime` reads the access time out of the stat the walk already did; `atimeIsRecorded` probes the real data_dir at startup (write a throwaway file, backdate it, read it, see whether atime moved) so a `noatime` mount is detected rather than silently degrading eviction to write-time-only. Depth: `docs/eviction.md`
- `compactkey.go` — `compactKey`: a cache key held as the 32-byte action ID inline, with `raw` set only for keys outside the cacheprog pattern. Comparable, so it doubles as a map key. The index, the eviction sweep and the access map each hold one per object, so the 80-byte-string form cost hundreds of MB and a GC object apiece at a million keys. Depth: `docs/memory-limits.md`

- `compression.go` (+ `compression_unix.go` / `compression_windows.go`) — **this server compresses nothing**: bodies arrive already lz4-compressed from the go-toolchain client, `PutStream` stores them byte-for-byte, GET serves them untouched, there is no gzip middleware or `Content-Encoding`, and the batch tar is uncompressed. The only decompression is the read-path guards peeking one lz4 block (memoized per key, see `cleanmemo.go`). That leaves exactly one place a second compression pass can hide -- the filesystem -- so at startup `logCompressionAdvisory` warns once when `data_dir` sits on a ZFS dataset with `compression` set: every stored body would be compressed a SECOND time, burning CPU on every write for approximately nothing (ZFS's early-abort limits but does not remove the attempt). Detection is a cheap `statfs` for the ZFS magic first (`dirIsZFS`), and only then the `zfs list`/`zfs get` probes for the dataset and its property; the probes are seams (`compressionProbes`) because no test can arrange a real dataset. Silent on every uncertainty -- not ZFS, dataset unidentifiable, property unreadable, or `compression=off` -- since an advisory nobody can act on is noise on every boot.
- `storage_unix.go` / `storage_windows.go` — Platform-specific file locking, user metadata xattrs, and server audit xattrs. Unix `setMetadata` writes PROTECTED keys first (`outputid`, `compression` — load-bearing for the protocol; any error on them still fails the PUT) and then degrades gracefully on optional keys: an `E2BIG`/`ENOSPC`/`EDQUOT` (the ext4 non-ea_inode ~4 KiB shared EA block vs the client's uncapped `Src` list) drops THAT key, counts `s3_metadata_xattrs_dropped_total`, and logs — instead of 500ing the PUT and making exactly the biggest packages uncacheable. `setMetadataFd`/`getMetadataValueFd` are the fd-scoped variants the self-heal stamps through (`unix.Fsetxattr`/`Fgetxattr`). Reads go through `isUserMetaAttr`, which excludes the audit namespace — `user.s3audit.` begins with `user.s3.`, so audit fields used to be read back as metadata and emitted as `X-Cache-Meta-Audit.*` headers, leaking the uploader's identity and IP to every client. `listXattrs`/`getXattrBuf` read into a stack buffer and only fall back to the size probe on `ERANGE` (halving the syscalls per metadata read). Windows keeps metadata in JSON sidecars with a full lifecycle: `finalizeSidecars` renames them with the body at PUT (they used to be orphaned under the temp name), `setMetadata` read-merges-writes (used to whole-file-replace, destroying other keys), `removeSidecars` cleans them on Delete/eviction, and `isSidecarName` keeps `Walk` from misreading sidecars as objects; compile-checked via `GOOS=windows`, untested on Windows

- `cacheclient/` — **the client side of this server's wire protocol, as its own Go module** (`github.com/wow-look-at-my/go-s3-server/cacheclient`). It covers single GET and PUT, `/_index`, `/_batch/get`, `/_batch/put`, lz4 framing, and the read guards. The guards are the outputid hash, the build-id action, and the module index. Protocol and server change together in one repo. A header or an endpoint therefore cannot drift between them. Its own `go.mod` keeps the dependency list to lz4 and `go-containers/set`. The server's cobra and prometheus tree stays out, because a consumer vendors this module into a tree that will not take them. Diagnostics go to a `Logger` the consumer installs. The default is silence. A caller whose stdout is a protocol channel must not have stderr written for it. The module carries NO tracing. Nobody can reimplement OpenTelemetry by hand here. Instrumentation waits on gosmopolitan compiler integration. Its consumer is gosmopolitan's `cmd/go`, which calls the cache in process. go-toolchain's `cacheprog` subcommand spawned it as a `GOCACHEPROG` subprocess. That subcommand is deleted.
- `main.go` — the CLI entry point, built on cobra. It serves in a goroutine and waits for `SIGINT` or `SIGTERM`. It then calls `srv.BeginShutdown()`, which flips `/_health` to 503. It then calls `httpSrv.Shutdown(ctx)` with a `shutdownTimeout` of 280s, kept under a typical container stop grace. In-flight requests thus drain before exit. A rolling-update `docker stop` no longer cuts them off.

- `server.go` — the HTTP router, the auth gate, client-IP resolution, the audit context, and bucket dispatch. The routes are `GET /_index`, `GET` or `POST /_batch/get`, `PUT /_batch/put`, and `GET`, `HEAD`, `PUT` and `DELETE` on object keys. POST is the sound method for the body-carrying batch lookup. GET stays for an older client. **Admission control**: a buffered `sem` channel sized to `max_concurrent_requests` bounds in-flight requests. A full channel sheds the excess with `503` and `Retry-After`. The server never queues to an OOM, which a proxy reports as `502`. `NewServer` defaults the limit. A directly-constructed `Config` is therefore safe too. **Health and readiness**: an unauthenticated `GET /_health` probe is handled at the very top of `ServeHTTP`, before logging, metrics, auth and admission control. It returns `200` and `ok` normally. It returns `503` once `BeginShutdown` sets the `shuttingDown` flag. A health-checking proxy in front then takes the instance out of rotation during graceful shutdown. The drain itself relies on `Shutdown` closing the listener, never on somebody watching the probe.
- **Update-check endpoints** — `GET /.well-known/docker-updater/{health,pre-update}` answer beside `/_health` at the top of `ServeHTTP`. They clear the same gates: auth, admission control and the access log. Both are aliases of the drain flag, not a second liveness implementation. Pre-update never holds an update for in-flight requests. A cache miss costs a rebuild. Nothing here is unrecoverable. The image EXPOSEs its serving port. docker-updater therefore finds these probes without the deploy naming `docker-updater.well-known.port`.
- `server_test.go` — the health and readiness endpoint tests. They cover `200` and ok, `503` while draining, and the bypass of both the auth gate and admission control.
- `handlers.go` — the object handlers `GetObject`, `PutObject`, `HeadObject` and `DeleteObject`. It also holds `handleGetIndex` for `/_index` and `writeError`, which writes a native plain-text error as a `<code>: <message>` body plus an `X-Cache-Error-Code` header. It also holds `storeOneObject`, the shared store path both the single PUT and `/_batch/put` go through. The two therefore cannot drift. Bodies stream in both directions. Nothing whole-object is ever buffered. Every read applies the module-index guard and then the outputid self-heal. Every single-object GET lands in `s3_get_requests_total{outcome}`. Depth: `docs/object-handlers.md`
- `cleanmemo.go` — the **known-clean key memo**. It is an in-memory set of indexed cacheprog keys whose stored body already passed the read-path module-index probe. It shards on the action hash's first byte. Both read guards consult it and skip the open and the lz4 decode on a hit. A warm key therefore pays the probe once, never per GET, batch or prefetch. The memo is invalidated wherever the body can change or vanish. Those places are an overwrite PUT, in `PutStream` after the rename, plus `Delete` and eviction in `evictOne`. All of them go through `Storage.forgetClean`. `maxCleanMemoEntries` bounds it. Past the bound it clears wholesale and repopulates by re-probing. Nil-safe accessors keep a directly-constructed `Storage` value working. The memo is a probe-skip optimization, not the safety boundary. The PUT guard remains the gate that keeps a new index out.
- `lrucache.go` — the **byte-bounded sharded LRU** every in-memory cache is built on. It holds a budget in bytes and evicts the least recently used entry to stay inside it. `SetBudget` changes the bound at runtime and evicts immediately. Each shard holds an equal slice of the budget. An insert therefore evicts only within its own shard. The hot path stays lock-local. An entry larger than its shard's whole budget is still held. A cache that refuses to hold anything is a permanent miss. The real bound is the budget plus at most one entry per shard.
- `memlimit.go` — **memory awareness**. The process ceiling sizes each cache's budget. `debug.SetMemoryLimit(-1)` reports GOMEMLIMIT or go-toolchain's injected cgroup guard. The cgroup files answer next. An unknown ceiling reads as zero. `memController` samples every 250ms and moves ONE number, the scale applied to those budgets. `resolveMemoryBudget` runs from `run()`, never from a package-level initializer. go-toolchain's injected `gomemlimit_gen.go` sets `GOMEMLIMIT` from an `init()`, at a fraction of the cgroup limit. A package variable initializes before any `init()`. Detecting early therefore reported the raw container limit, a ceiling nothing enforced. The server never installs a limit of its own. Above 85% in use it halves the scale, evicts, and returns memory to the OS. Below 65% in use it grows the scale back. At the floor it stops and logs that the container needs more memory. **It cannot touch request handling.** A cache server that refuses to serve is useless, because every client it turns away rebuilds anyway. An unknown budget disables the controller and leaves the fixed defaults. Metrics: `s3_memory_{limit,in_use}_bytes`, `s3_memory_shrinks_total`, `s3_cache_memory_bytes{cache}` and `s3_cache_memory_budget_bytes{cache}`. Depth: `docs/memory-limits.md`
- `metacache.go` — the **per-key metadata cache**. It holds an object's user metadata against the mtime and size it was read under. A warm `Stat` or `Open` therefore skips the `listxattr` and the per-attribute `getxattr`. That work costs about 42us per key. A batch pays it for every key it touches. The cache is self-validating. A hit is served only when the fresh stat matches. An overwrite makes a new inode. Stale metadata therefore cannot be served. An xattr stamped onto a LIVE inode is the one case the stat cannot see. That is the outputid self-heal, which drops the entry explicitly through `forgetMeta`. `Delete`, `SetMeta` and eviction drop it too. The cache is bounded and clears wholesale. Metrics: `s3_meta_cache_hits_total` and `s3_meta_cache_misses_total`. Depth: `docs/hot-path-cpu.md`
- `cacheversion.go` — the `data_dir` format version in `currentCacheVersion`, its startup purge, and the `.tmp-*` orphan sweep. It was split out of `storage.go`. Both run once, before serving, under the data_dir's exclusive lock.
- `selfheal.go` — **in-place** self-healing for a cache object that lacks `outputid` metadata, the GOCACHEPROG content address. Such an object is a relic of an earlier cache-data iteration, or a `data_dir` move stripped its xattrs. A client cannot verify the body without the outputid. It therefore discards the download and rebuilds, logging `missing outputid metadata`. The key stays advertised in `_index`, so a client skips re-uploading it. The result is a permanent forced miss. The fix is **repair, not eviction**. `outputID` is by definition the `sha256` of the decompressed body. So `reconstructOutputID` lz4-decompresses the stored body, streamed straight into the hash with no whole-object buffering. It recomputes the outputid and persists it **through the same file descriptor it hashed**, with `setMetadataFd` calling `unix.Fsetxattr`. It writes only that one xattr. The body, the audit xattrs and the `_index` entry stay untouched. Fd-based stamping fixes the stale-stamp race. The old path-based `storage.SetMeta` landed the OLD inode's hash on a body a concurrent overwrite PUT had just renamed into place. That left `outputid != sha256(body)` permanently. Every client then discarded the download and never re-uploaded. On the GET path the repair hashes the handler's own serve handle and rewinds it. A failed rewind fails the repair rather than serving a consumed fd. The emitted outputid therefore always describes the exact bytes streamed. The batch paths pass nil. The repair then opens and stamps a private raw handle through `openRaw`, with no access record and no op metric. A pre-existing outputid that DISAGREES with the just-computed body hash is counted in `s3_outputid_mismatch_total` and corrected in place. `missingOutputID` is the predicate. `ensureOutputID(storage, key, meta, f)` orchestrates the repair, mutates the in-memory `meta` to carry the reconstructed outputid, and bumps `s3_self_heal_repairs_total`. It is **scoped to an indexed cacheprog key**, `go-buildcache/v1<64-hex>`, through `extractActionHash`. Those are the only keys advertised in `_index`. They are therefore the only ones with the skip-re-upload permanent-miss problem. Any other key carries no cache-protocol contract and is served exactly as stored. An arbitrary non-cache object is thus never touched. `handlers.go` applies the repair on **read** for a single GET. `batch.go` applies it in the requested-key loop and the prefetch scan. The repair is one-time, because the next read sees the outputid. A body that cannot be decompressed is unusable by the client regardless. It is **left on disk but DE-ADVERTISED**. `ensureOutputID` returns false, counts `s3_self_heal_failures_total`, and drops the key from `/_index` through `Index.Remove`. The file stays for forensics and for the eviction policy. The caller reports a clean miss. De-advertising matters. A client skips re-uploading an indexed key. An unrepairable but advertised key was therefore a permanent forced miss. Unindexed, the next consumer re-uploads a good body and heals it. A startup or sweep-end rebuild re-advertises it from disk until then. That churn is bounded. It is strictly better than the wedge. Deleting the body here is still deliberately avoided, because an evict-and-re-upload churn pipeline cannot be audited. **Note** the module-index guard in `modindex.go` runs at these same read points, before this self-heal. It is the opposite policy. A module-index blob is *evicted*, refused and deleted, and counted in `s3_module_index_evictions_total`. Unlike an object with no outputid, it can never be made usable.
- `deprecation.go` — the backward-compatibility shims for the retired S3 protocol. It defines the native `x-cache-meta-` and legacy `x-amz-meta-` metadata header prefixes. It also defines `noteDeprecatedS3Meta`. That function logs a one-time `DEPRECATION:` warning, because a CI run issues thousands of PUTs and per-request logging floods the log. It increments `s3_deprecated_requests_total{feature="amz_meta_header"}` on every legacy request.
- `modindex.go` and `lz4head.go` — the **module-index guard**. This shared cache must never hold a Go module index. Such an index carries no build id and does not bind to its action key. A mis-keyed one breaks every consumer's build at package load. The guard refuses it on PUT. It evicts it on read, for an indexed cacheprog key, on GET, batch and prefetch. The verdict comes from an lz4 frame-header walk that reads the first literal run instead of decoding a block. That walk costs about 183ns, allocates nothing, and holds for any object size. It falls back to a real decode for any frame shape it cannot fully parse. Depth, invariants and history: `docs/module-index-guard.md`
- `index.go` — the in-memory key index. It maintains an mtime-sorted list of `indexEntry` for `_batch/get` prefetch. An entry is a `compactKey` plus an mtime, so a million-key index carries no per-key allocation. It also maintains a sorted slice of action-ID hashes. That slice serializes to the GBCI v1 binary blob served at `GET /<bucket>/_index`. A PUT appends to the unsorted `pending` buffer of hashes and the `pendingEntries` buffer of mtimes, under a microsecond-scale mutex. The hash sort, dedupe and serialize wait for the next `Blob()`. The mtime merge and sort wait for the next `NearbyKeys` or `Remove`, through `drainEntriesLocked`. Both stay off the per-PUT path. A PUT is therefore an O(1) append. A writer never convoys on a global sort. A drain releases a pending buffer grown past `maxRetainedPending`, rather than holding a rebuild-sized array forever. **Rebuild merges, never clobbers.** `rebuild` streams `Storage.Walk` into an `indexBuild`, sorted and deduped off-lock. `applyRebuild` installs it while PRESERVING the pending buffers. The old rebuild nil'd both. It silently dropped every PUT that completed during the multi-second walk, from `/_index` until the next rebuild. **`RemoveKeys`** batch-drops a victim set of entries, hashes and pending in one O(n+v) filter pass. The eviction sweeper calls it BEFORE unlinking any file. A key is therefore never advertised but deleted mid-sweep. **`Contains`** is the O(log n) plus O(pending) membership probe behind the `miss_advertised_unservable` GET outcome. **ETag purity**: the serialized `generation` header field is CONTENT-DERIVED, from the leading bytes of the hash body's digest. It is not a serialization counter. The blob, and therefore the ETag, is a pure function of the advertised key set. Duplicate-only PUT traffic and a restart reserialize byte-identically. A client keeps getting a 304. The client never reads the field. It validates only the magic, the version, the hash size, the length and the trailer. The size gauges `s3_index_entries`, `s3_index_hashes` and `s3_index_pending_hashes` update at every mutation. A full rebuild is timed in `s3_index_rebuild_duration_seconds`.
- `batch.go` — the tar batch endpoints. **`handleBatchGet`** serves `/_batch/get`, on GET or POST. POST is preferred, because the request carries a JSON body and a GET with a body is proxy-hostile. The first phase stats the requested keys. The module-index guard and the self-heal gate each one. The second phase streams the found bodies into a tar, after a `manifest.json`. Prefetch is ordered for cheapness. `NearbyKeys` candidates are **tracker-suppressed FIRST**, by `prefetchTracker.filterKeys`, which is one map lookup per key. Only a survivor pays the stat, guard and heal work in `buildPrefetchEntries`. Only a key actually included in the response is recorded as sent, through `tracker.record`. A candidate the guard dropped therefore stays eligible later. The guard peek and the self-heal use raw opens, with no `get` op metric and no last-access stamp. A batch of N served keys therefore performs exactly N counted gets. A prefetch candidate never gains LRU lifetime it did not earn. Volume lands in `s3_batch_requests_total` and `s3_batch_keys_total{kind=requested|found|prefetched|suppressed|streamed}`, as well as in the log line. **`handleBatchPut`** serves PUT `/_batch/put` with Content-Type `application/x-tar`. It is the bulk-upload counterpart. The go-toolchain client issues one HTTP PUT per cached object. A CI build produces thousands of them. Each one takes an admission-control `sem` slot and saturates the server, which sheds uploads with a 503. `/_batch/put` accepts a tar of many objects in ONE request, holding ONE sem slot. The tar carries `manifest.json` as its FIRST member, then one `data/<key>` member per entry, in manifest order. The manifest is `{"entries":[{"key":...,"metadata":{name→value, keyed by lowercased meta name without the `X-Cache-Meta-` prefix}}]}`. The shared `storeOneObject` stores each member. The response is JSON, `{"results":[{"key":...,"status":"stored|dropped|conflict|error","message":...}]}`, with one result per manifest key. A per-member store failure is recorded as `error` and does NOT abort the batch. `http.MaxBytesReader` bounds the whole batch body at `maxBatchKeys` times `max_object_bytes`, and answers 413 over it. Entries are capped at `maxBatchKeys`, again 413 over. Each member is bounded to `max_object_bytes`. Several shapes fail the whole request with a 400 `invalid_request`. They are a malformed tar, a missing or late `manifest.json`, and a duplicate key. A data member with no manifest entry fails too, as does a manifest entry with no data member. The request-level audit of uploader, IP, user agent and timestamp is shared across members. `cloneAudit` clones it per member, because `PutStream` writes a per-member `content_length`. A module-index member is refused inside the shared `storeOneObject`. It is recorded as `dropped` and counted in `s3_put_refusals_total`, exactly like a single-PUT refusal. Per-batch volume is visible through the `route="BatchPut"` HTTP metrics and the `batch put: entries=… stored=… dropped=… conflict=… error=…` log line.
- `storage.go` — the filesystem storage, with two-level key sharding. It holds single-key `Delete`, used by DeleteObject. It also holds single-key `SetMeta`, which adds or overwrites a specific metadata xattr in place without touching the body or another xattr. The outputid self-heal in `selfheal.go` uses it. Bodies are streamed, never buffered. `PutStream` copies to a temp file, then applies write_once through the streaming `filesEqual`. `Open` returns an `*os.File` and the meta, for a streaming read. `Stat` returns the meta and size with no body. Those back the GET and batch paths. `Put([]byte,...)` is a thin wrapper over `PutStream`, for an in-memory caller and for a test. `openRaw` opens a body with NO storage-op metric and NO last-access recording. It serves an internal peek, such as the module-index guard or the self-heal hashing, which is never a client-visible serve. `OpenBody` is `Open` minus the metadata read. It opens, takes the size, records last access, and counts the same `get` op. The batch streaming phase uses it, because its manifest already carries the metadata. **Durability**: `PutStream` fsyncs a temp file at or above `fsyncThresholdBytes` before the rename. A small object skips the fsync, because the client hash-verifies every download. `NewStorage` sweeps an orphaned `.tmp-*` file at startup. Such a file is invisible to `Walk` and to eviction. It otherwise leaks disk forever. The sweep is safe, because the exclusive flock guarantees no in-flight writer. `PutStream` also invalidates the known-clean memo through `forgetClean` after every rename. `finalizeSidecars` moves the Windows metadata sidecars along with the body, and does nothing on unix. `Storage` also carries `cleanKeys`, the known-clean memo in `cleanmemo.go`, and `metaCache`, in `metacache.go`. `Walk(fn)` is the metadata-only enumeration of key, size, mtime and atime. Both the index rebuild and the eviction sweep are built on it. It takes a callback rather than a slice, because materializing a million keys as strings was this process's largest allocation. `storage.go` also holds **last-access tracking** for eviction. `accessShards` is a sharded in-memory map keyed by `compactKey`. `recordAccess` updates it on every `Open` and `Get`. It is allocated only when `EnableAccessTracking` is called. `main.go` calls that only when the data_dir does not record file access times, because the filesystem's own atime is durable and free. Access time is kept *separate* from mtime. mtime stays the write time the prefetch system depends on.
- `eviction.go` — background cache pruning. It is an **LRU bounded by `max_bytes`**, with `max_age` as an off-by-default TTL. `Evict(maxAge, maxBytes, now)` walks the data_dir twice and never lists it. The first walk measures total bytes plus a bounded last-use histogram. From that it derives ONE cutoff, `max(ageCutoff, sizeCutoff)`. The second walk deletes everything below the cutoff, in batches. Each batch is **de-advertised from `/_index` before its files are unlinked**. The walk then rebuilds the index once, as a true-up. `evictOne(key, expectMtime)` re-stats before deleting, which closes the overwrite TOCTOU. It drops the access record, the known-clean memo and the Windows sidecars. Last use is `max(mtime, atime, in-memory record)`. The in-memory `accessShards` map exists only when the data_dir does not record access times. `RunEvictionLoop` schedules from the `.last_sweep` marker. It sweeps at startup when a full interval has passed, and otherwise waits out the remainder. It refreshes `s3_cache_bytes` every 15 min. `main.go` wires it up only when `Eviction.Enabled()` answers true. Otherwise main logs a loud unbounded-growth warning. Depth: `docs/eviction.md`
- `atime.go`, with `atime_linux.go`, `atime_windows.go` and `atime_other.go` — durable last-use. `fileAccessTime` reads the access time out of the stat the walk already did. `atimeIsRecorded` probes the real data_dir at startup. It writes a throwaway file, backdates it, reads it, and sees whether atime moved. That detects a `noatime` mount, rather than silently degrading eviction to write-time only. Depth: `docs/eviction.md`
- `compactkey.go` — `compactKey`, a cache key held as the 32-byte action ID inline. `raw` is set only for a key outside the cacheprog pattern. The type is comparable. It therefore doubles as a map key. The index, the eviction sweep and the access map each hold one per object. The 80-byte string form therefore cost hundreds of MB and a GC object apiece at a million keys. Depth: `docs/memory-limits.md`
- `eviction_test.go` — the eviction tests. They cover age, access-time survival, size and LRU, the index rebuild, access-record cleanup, and Duration and config parsing.
- `storage_test.go` — the cache version and purge tests.
- `compression.go`, with `compression_unix.go` and `compression_windows.go` — **this server compresses nothing**. Bodies arrive already lz4-compressed from the go-toolchain client. `PutStream` stores them byte-for-byte. GET serves them untouched. There is no gzip middleware and no `Content-Encoding`. The batch tar is uncompressed. The only decompression is the read-path guards peeking one lz4 block, memoized per key in `cleanmemo.go`. That leaves exactly one place a second compression pass can hide, the filesystem. So `logCompressionAdvisory` warns once at startup when `data_dir` sits on a ZFS dataset with `compression` set. Every stored body then gets compressed a SECOND time. That burns CPU on every write for approximately nothing. The ZFS early-abort limits the attempt, but does not remove it. Detection asks a cheap `statfs` for the ZFS magic first, in `dirIsZFS`. Only then does it run the `zfs list` and `zfs get` probes for the dataset and its property. The probes are seams, in `compressionProbes`, because no test can arrange a real dataset. The advisory is silent on every uncertainty. Those are a filesystem that is not ZFS, an unidentifiable dataset, an unreadable property, and `compression=off`. An advisory nobody can act on is noise on every boot.
- `storage_unix.go` and `storage_windows.go` — platform-specific file locking, user metadata xattrs, and server audit xattrs. Unix `setMetadata` writes the PROTECTED keys first. Those are `outputid` and `compression`, which are load-bearing for the protocol. Any error on them still fails the PUT. It then degrades gracefully on an optional key. An `E2BIG`, `ENOSPC` or `EDQUOT` drops THAT key, counts `s3_metadata_xattrs_dropped_total`, and logs. The cause is the ext4 non-ea_inode shared EA block, about 4 KiB, against the client's uncapped `Src` list. A 500 on the PUT instead makes exactly the biggest packages uncacheable. `setMetadataFd` and `getMetadataValueFd` are the fd-scoped variants the self-heal stamps through, over `unix.Fsetxattr` and `Fgetxattr`. Reads go through `isUserMetaAttr`, which excludes the audit namespace. `user.s3audit.` begins with `user.s3.`. Without that exclusion an audit field reads back as metadata and is emitted as an `X-Cache-Meta-Audit.*` header. That leaks the uploader's identity and IP to every client. `listXattrs` and `getXattrBuf` read into a stack buffer. They fall back to the size probe only on `ERANGE`, which halves the syscalls per metadata read. Windows keeps metadata in JSON sidecars, with a full lifecycle. `finalizeSidecars` renames them with the body at PUT. A sidecar is therefore never orphaned under the temp name. `setMetadata` reads, merges and writes. It therefore never destroys another key. `removeSidecars` cleans them on Delete and on eviction. `isSidecarName` keeps `Walk` from misreading a sidecar as an object. The Windows path is compile-checked through `GOOS=windows` and untested on Windows.
- `lock_windows.go` — Windows file locking, through syscall.
- `handlers_test.go` — the unit tests for the handlers.
- `modindex_test.go` — the tests for module-index detection and the PutObject refusal.
- `dats/` — the executable spec for the HTTP surface. `api.dats` covers the roundtrip, not_found, overwrite, sharding, native and legacy metadata, `/_index` and its ETag, the unauthenticated health probe, and the refusals. `writeonce.dats` covers the store, an idempotent resend, a 409 on different bytes, and sharding. Every test starts its own server on its own port, through the shared `serve.sh`. No two tests therefore share a resource. `go-toolchain` runs the suites after the build. `dats dats/*.dats` runs them alone against `./build/go-s3-server`, and `SERVER=` picks another binary. The client and server round trip is NOT here. It is `cacheclient_wire_test.go`, because the sandbox has no network, does not mount the toolchain cache, and carries only a stock `go`.
- `cacheclient_wire_test.go` — the round trip over the real protocol. `cacheclient` uploads through the PUT coalescer. A SECOND backend, holding no local state, must then be served every body off the server. The test checks that against `s3_batch_keys_total{kind="streamed"}`. Each body must hash to the output ID it came back under. The root module takes a `replace` onto `./cacheclient`. This test therefore runs against the tree. It is a Go test rather than a dats suite, because gosmopolitan's `cmd/go` calls cacheclient in process. No build spawns a cacheprog subprocess.
- `.github/workflows/ci.yml` — CI. The `test` job checks out, installs bubblewrap for the dats sandbox, and runs `wow-look-at-my/go-toolchain@master`. That action also autoreleases the binary to buildhost. No job carries an assertion of its own. Every assertion lives in `dats/` or in a Go test. A contributor therefore runs exactly what CI runs.
- **This repo ships no Dockerfile, on purpose.** buildhost synthesizes a runnable image from the uploaded binary, at `oci.pazer.build/v2/go-s3-server`. It sets the entrypoint, `WorkingDir`, `Env` and `User` itself, and its own tests cover starting a synthesized APE image. A hand-rolled Dockerfile here re-solves all of that, including the APE shell-header start. Depth: `docs/formats/oci.md` in buildhost. The deploy bind-mounts a host directory at `/var/lib/go-s3-server` and passes its own `--config`. A restart without that mount costs every client a full rebuild.

## Conventions

- CLI parsing uses cobra. The single root command is in `main.go`.
- Error responses are native plain text (`writeError`: `<code>: <message>` body, `Content-Type: text/plain`, machine-readable code in the `X-Cache-Error-Code` header). Codes are snake_case (`not_found`, `unknown_bucket`, `access_denied`, `overloaded`, `conflict`, `too_large`, `method_not_allowed`, `invalid_request`, `internal_error`) — not S3 XML/error codes. The `/_index` endpoint serves a binary GBCI v1 blob (`application/octet-stream`) with a strong ETag (hex-encoded SHA-256 trailer); conditional GETs are handled by `http.ServeContent`. `PUT /_index` accepts a GBCI v1 blob from clients and merges its action-ID hashes into the in-memory index.
- Object metadata is stored in filesystem extended attributes (xattr on Unix, ADS on Windows).
- Error responses are native plain text. `writeError` writes a `<code>: <message>` body with `Content-Type: text/plain`. It puts the machine-readable code in the `X-Cache-Error-Code` header. The codes are snake_case: `not_found`, `unknown_bucket`, `access_denied`, `overloaded`, `conflict`, `too_large`, `method_not_allowed`, `invalid_request` and `internal_error`. They are not S3 XML error codes. The `/_index` endpoint serves a binary GBCI v1 blob as `application/octet-stream`, with a strong ETag from the hex-encoded SHA-256 trailer. `http.ServeContent` handles a conditional GET.
- Object metadata lives in filesystem extended attributes: xattr on Unix, ADS on Windows.
- Storage keys are sharded: `prefix/v1aabbccdd` → `prefix/v1/aa/bbccdd`.
- `write_once` config is an object: `{"action": "allow"|"deny", "notification": "never"|"always"|"content_differs"}`. Defaults: `action=allow`, `notification=never`.
- HTTP Basic Auth uses `username` and `password` credentials. To run without auth, set `disable_auth: true` and omit `credentials`. An empty string in a credential entry is a config error. There is no empty-string convention for disabling auth.
- `credentials` config is required unless `disable_auth: true`. Each entry needs both `username` and `password` set to non-empty values.
- A string config value supports an env var reference. `{"type": "envvar", "name": "VAR_NAME"}` resolves to `os.Getenv("VAR_NAME")` at load time. The `ConfigString` type carries it. An env var that resolves to `""` is rejected the same as a literal empty string. An unset env var therefore cannot silently disable auth.
- Every `PutObject` persists audit metadata as extended attributes on the stored file. The attributes are `user.s3audit.uploader`, `user.s3audit.uploaded_at`, `user.s3audit.client_ip`, `user.s3audit.user_agent` and `user.s3audit.content_length`. The `user.s3audit.*` namespace is separate from a user-supplied metadata header. A native `X-Cache-Meta-*` or a deprecated `X-Amz-Meta-*` header is stored as `user.s3.*`. User metadata therefore cannot spoof an audit field. The `user.s3*` xattr prefixes stay until the repo rename. On Windows the audit is a JSON sidecar at `<path>.audit`.
- The client IP resolves in this order: `CF-Connecting-IP`, then `X-Real-IP`, then the first entry of `X-Forwarded-For`, then `r.RemoteAddr`. The server trusts these proxy headers unconditionally. Deploy it only behind a trusted reverse proxy.
- Cache version: `cacheversion.go` stamps the `data_dir` with a `.cache_version` file. `currentCacheVersion` is a constant there. At startup the server compares the stored version against the current one. A missing marker reads as version 1. A difference removes every entry in `data_dir` before serving. Bump `currentCacheVersion` to force an operator to rebuild the cache after a change that invalidates prior contents. Version 3 purges a cache that may hold a poisoned Go module-index object. A mis-keyed index breaks a consumer's build with `package runtime is not in std` or `corrupt index`. The purge repairs every client at once. The PutObject refusal above keeps a new one out. Version 4 purges an entry that the retired executable-cache path stored as a DIRECTORY holding a file named for the binary. Every entry is one plain file now, so such an entry is unreadable. A missing key is simply rebuilt.
- `eviction` config is an object: `{"max_bytes": 53687091200, "max_age": "0", "interval": "24h"}`. The cache is an **LRU**. `max_bytes` is a `*int64`. An absent field therefore takes `CACHE_MAX_BYTES` or `defaultEvictionMaxBytes`. An explicit `0` disables the size budget. `max_age` is a plain `Duration` that defaults to 0. The TTL is opt-in, because a build-cache entry that is still read is still useful. With both off the cache grows without bound. The server then logs a startup warning. `max_age` and `interval` are Go duration strings, or seconds, parsed by the `Duration` type in `config.go`. Eviction is driven by *last use*, `max(mtime, atime, in-memory record)`. It never rewrites mtime. The prefetch grouping that keys on mtime is therefore unaffected. Depth: `docs/eviction.md`
- The `CACHE_MAX_BYTES` env var sets the size budget without a config edit. It takes a byte count or a size such as `100GB`, parsed by `parseByteSize` in powers of 1024. An explicit `eviction.max_bytes` wins. A value that is set but unparseable fails startup, rather than silently reverting to the default.
- Metrics carry the `s3_` prefix until the rename. HTTP: `s3_http_requests_total`, the duration and size histograms, `s3_http_in_flight_requests` and `s3_http_rejected_total`. Per-outcome GETs: `s3_get_requests_total{outcome=hit|miss_not_found|miss_advertised_unservable|miss_module_index_evicted|miss_peek_error|miss_selfheal_failed}`. `miss_advertised_unservable` is the index and store divergence tripwire. It must stay near zero. PUT refusals: `s3_put_refusals_total{reason="module_index"}`, whose movement during CI is the PUT guard's liveness proof. Batch volume: `s3_batch_requests_total` and `s3_batch_keys_total{kind}`. Index health: `s3_index_entries`, `s3_index_hashes`, `s3_index_pending_hashes` and `s3_index_rebuild_duration_seconds`. Storage ops have their own counters. Eviction: `s3_evictions_total`, `s3_evicted_bytes_total`, and `s3_cache_bytes`, which refreshes every 15 min rather than only at sweep end. Self-heal: `s3_self_heal_repairs_total` for a repair in place, `s3_self_heal_failures_total` for an unrepairable and de-advertised key, and `s3_outputid_mismatch_total` for stale-stamp corruption found and corrected. The on-read module-index guard reports `s3_module_index_evictions_total`. The metadata cache reports `s3_meta_cache_hits_total` and `s3_meta_cache_misses_total`. On a warm cache that ratio IS the read path's CPU story. Xattr degradation reports `s3_metadata_xattrs_dropped_total`. Auth and deprecation have their own counters. A metrics listener that fails to bind does not kill the server. It logs and runs without metrics. `statusRecorder` forwards `io.ReaderFrom`. A GET body copy therefore keeps the sendfile path.
