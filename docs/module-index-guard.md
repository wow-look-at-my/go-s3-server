# The Go module-index guard

Why this server refuses to store or serve a Go module index, how it decides,
and what the decision costs. `modindex.go` + `lz4head.go`.

## How the verdict is reached

The magic is `go index v` at the very start of the DECOMPRESSED body, and
bodies arrive lz4-compressed. Recovering those ten bytes used to mean decoding
the body's whole first lz4 block -- up to the client's 4 MiB block size -- on
every PUT and every cold read: 77us of pure CPU for a 256 KiB object, paid
thousands of times per CI burst.

It is now a header walk (`lz4LeadingBytes`, `lz4HasPrefix` in `lz4head.go`):
an lz4 frame's first block always opens with a literal run, and literals are
stored verbatim, so the leading decompressed bytes are read straight out of the
frame -- frame header, block size, token, literals. 183ns, no allocation, no
decompression, independent of object size.

The walk is an optimization, never a second source of truth. It reports "cannot
tell" for every shape it does not fully understand (truncated head, non-frame
magic, unknown version, dictionary frame, empty frame, a literal run that
matches the magic so far but is shorter than it), and the caller then decodes
for real exactly as before. `TestModuleIndexGuard_FastPathMatchesSlowPath` and
`TestLz4LeadingBytes_AgreesWithDecoder` pin the agreement; the undecidable
shapes are enumerated in `TestLz4LeadingBytes_UndecidableShapes`.

A short literal run still settles the common case: a compiled Go object starts
`!<arch>`, which diverges from `go index v` within four bytes.

## The rest of the guard

`looksLikeGoModuleIndex`: detects a Go module index blob (optionally lz4-compressed) via the `go index v` magic. **The detection decodes the body's full first lz4 block, NOT a fixed-size compressed peek** — this is the load-bearing correctness point. The go-toolchain client packs each cached body into a **single lz4 block**, and pierrec/lz4's reader needs the **entire** block before it can decode any output. The guard used to peek only the first **512 compressed bytes** (`const indexPeekBytes = 512`) and lz4-decompress that prefix; but real module indexes compress to **521 B – ~36 KB** (always > 512), so the reader, handed a truncated 512-byte prefix, returned `n=0` (unexpected EOF), the magic was never seen, and **the poison was served on READ and stored on PUT** — both paths broken by the same truncation. (The old synthetic test passed only because its 2 KiB-of-`x` payload compressed to ~61 bytes, fitting in 512 — non-representative; verified against 5 real `s3.pazer.io` blobs that the old code returned false for all and the fix returns true for all.) The fix feeds the detector enough input to decode the first block: `indexMagicProbeBytes` (16) decompressed bytes are read, and the **read path streams an `lz4.Reader` straight off the open file** (it pulls exactly one block, however large), while the **PUT path reads a bounded but block-sized prefix** (capped at `indexPutPeekBytes`, 1 MiB — comfortably above the observed ~36 KB max and well below lz4's 4 MiB block ceiling). **The PUT peek self-sizes to the body** (`io.ReadAll(io.LimitReader(body, indexPutPeekBytes))`), allocating ~the body's actual size while `LimitReader` still caps the worst case at exactly `indexPutPeekBytes` — detection input is byte-identical to the old fixed cap. This replaced a `make([]byte, indexPutPeekBytes)` + `io.ReadFull` that pre-allocated the **full 1 MiB on every PUT** regardless of body size (a measured ~1 MB/op of pointless allocation churn): under a CI burst of ~7000 PUTs that thrashed GC and **saturated the admission-control `sem`**, shedding excess PUTs with `503` so nothing got stored/indexed — the next build then saw an empty `/_index` (`hits=0`) and blew the second-build time gate. The detection cap stays at 1 MiB (it bounds only the worst case now, not every PUT), so a real index's first block is always fully covered. Used to refuse a module index on **both** the write **and** read paths. **Write (PutObject):** the unscoped peek-and-refuse — any upload whose first block decodes to the magic is dropped (200, stored nothing) on any key; a non-index body is stitched back via `io.MultiReader` and stored intact (large bodies keep streaming). **Read (GET, batch get, prefetch):** `evictModuleIndexOnRead` (for a GET that holds the open file — detects via `readIsModuleIndex` streaming the `lz4.Reader` over the file, then `Seek(0)` rewinds so the non-index serve path is byte-for-byte unchanged) and `evictModuleIndexOnReadByKey` (the batch variant — opens-peeks-closes, since those paths Stat-then-stream and must decide before building the manifest) detect a module-index blob already on disk, **evict it** via `evictModuleIndex` → `storage.Delete` (drops the file and the `/_index` entry, the same lever DeleteObject uses), bump `s3_module_index_evictions_total`, and signal a miss so the client recomputes the index locally. Both read variants are **scoped to indexed cacheprog keys** (`go-buildcache/v1<64-hex>`, via `extractActionHash`) — exactly like the outputid self-heal — so an arbitrary/non-cache object is never inspected or touched. This is what removes already-stored poison: the PUT guard only blocks NEW indexes, while a blob uploaded before the guard existed (and surviving because the one-time v3 startup purge already ran) was otherwise served verbatim on every GET and re-advertised in `/_index` on every restart, with the client — which never re-uploads an index and has no remote DELETE — refusing and re-fetching it forever. The read guard sheds each poisoned key on its **first post-deploy fetch** (a lazy, incremental self-heal that needs no cache-wide `currentCacheVersion` bump and works regardless of client version). It runs orthogonally to, and **before**, the outputid self-heal: a module index carries an outputid, so `ensureOutputID` would pass it. A garbled-but-READABLE `lz4` body is treated as not-an-index (fail-open) on read, never an error that would fail the serve path; a genuine source I/O error, however, is now distinguished (`errTrackingReader` wraps the source) and surfaces as a refused serve — `guardPeekError` → `miss_peek_error` — instead of fail-opening into a 200 that dies mid-copy. The GET-path guard returns a three-way `readGuardVerdict` (`guardServe`/`guardEvicted`/`guardPeekError`) so the distinct miss reasons are counted. **Perf**: every probe calls `zr.Reset(nil)` after the 16-byte magic read, returning pierrec/lz4's two pooled 4 MiB buffers — an abandoned reader never returns them, and before this fix every peek churned ~8.4 MiB of allocation on every GET/PUT/batch/prefetch inspection (BenchmarkPutObjectPeek: 8.49 MB/op → ~133 KB/op). Repeat probes are skipped entirely via the known-clean memo (`cleanmemo.go`), and the batch peek opens through `storage.openRaw` so it neither double-counts the "get" storage op nor stamps last-access onto candidates that are never served. Pairs with the go-toolchain client, which also refuses to upload/serve/ingest index blobs.
