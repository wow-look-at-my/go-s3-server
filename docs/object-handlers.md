# Object handlers

The request-path detail behind the one-line `handlers.go` entry in CLAUDE.md,
extracted verbatim so it can grow without being re-read on every request of
every session.

object handlers (GetObject, PutObject, DeleteObject) plus `handleGetIndex` for the `/_index` endpoint, and `writeError` (native plain-text error responses: `<code>: <message>` body + `X-Cache-Error-Code` header, replacing the old S3 XML `<Error>`). Metadata travels in native `X-Cache-Meta-*` headers; PutObject also reads the deprecated `X-Amz-Meta-*` (filling only gaps native didn't set) and calls `noteDeprecatedS3Meta` when it sees one; GetObject emits **both** prefixes so old clients still read the outputid. **Self-heal**: when an indexed cacheprog object (`go-buildcache/v1<64-hex>`) has no `outputid` metadata, GetObject repairs it **in place** (`ensureOutputID` in `selfheal.go`) — reconstructs the outputid from the body (`outputID == sha256` of the decompressed body) and persists it fd-based via `setMetadataFd` (see `selfheal.go`), then serves the object as a hit; the body, audit xattrs, and `_index` entry are all preserved (no eviction, no re-upload). A body that cannot be decompressed is reported as a clean `404`, counted, DE-advertised from `/_index`, and left on disk for the normal eviction policy. Non-cacheprog keys are served as stored. GetObject and PutObject **stream** bodies (no whole-object buffering): GET `io.Copy`s from `storage.Open`; PUT streams via `storage.PutStream` wrapped in `http.MaxBytesReader(max_object_bytes)` (413 over the limit). PutObject **refuses Go module-index blobs**: it peeks a bounded but block-sized prefix of the upload (`io.ReadAll(io.LimitReader(body, indexPutPeekBytes))`, capped at `indexPutPeekBytes` = 1 MiB — the read **self-sizes** to the body's actual length rather than pre-allocating the full cap, so a typical small object allocates ~its own size, not 1 MiB; see the `modindex.go` bullet for why) and, if it decompresses to the `go index v` magic (`looksLikeGoModuleIndex` in `modindex.go`), accepts the request (`200`) but stores nothing — a mis-keyed module index poisons every consumer's build at package load and this shared Go build cache must never hold one (the client recomputes the index locally on the resulting miss); a non-index body is stitched back together via `io.MultiReader` and stored intact. GetObject **also refuses + evicts a module-index blob on READ** (`evictModuleIndexOnRead`, scoped to indexed cacheprog keys), running it **before** the outputid self-heal: it streams an `lz4.Reader` over the already-open file to recover the magic (`readIsModuleIndex`), and on a hit `storage.Delete`s the object (file + `/_index` entry) and returns `404` (a clean miss) instead of serving the poison; on a non-hit it `Seek(0)`s the file back so the served body is byte-for-byte unchanged. (The detection decodes the body's **full first lz4 block**, not a fixed 512-byte peek: the client packs each body into a single lz4 block and pierrec/lz4 needs the whole block to decode any output, so a real index — compressing to 521 B – ~36 KB, always > 512 — was never recognized under the old fixed peek, on either the read-evict or the PUT path.) This is the lazy, per-key self-heal that removes module-index poison **already on disk** (the PUT guard only blocks new ones) — see the `modindex.go` bullet — with **no `currentCacheVersion` bump**. PutObject writes audit xattrs (`content_length` is filled in by PutStream from the bytes actually streamed). The module-index refusal is **counted and logged** (`s3_put_refusals_total{reason="module_index"}` + a per-refusal log line naming the key) — the counter moving during CI activity is the guard's liveness proof, closing the blind spot that hid the 512-byte-peek bug; a refused PUT never reaches `Index.Put` (that call sits after PutStream's rename), so a refused key is never advertised. Every single-object GET lands in `s3_get_requests_total{outcome}`: `hit`, `miss_not_found`, `miss_advertised_unservable` (404 on a key whose action hash `Index.Contains` still reports advertised — the index/store-divergence signature, should be ~0), `miss_module_index_evicted`, `miss_peek_error` (guard could not inspect/rewind), `miss_selfheal_failed`. The GET body copy keeps `f` as the direct `io.Copy` source (preserving the ReadFrom/sendfile path) and logs disk-side copy failures (`*fs.PathError`) — client disconnects stay unlogged. `handleHeadObject` answers `HEAD /{bucket}/{key}`: Stat-based, the exact GET header surface (both meta prefixes + Content-Length + Last-Modified), no body, no guard probe, no self-heal, no last-access stamp. DeleteObject is idempotent (204 even for a missing key) and is the surgical eviction lever for a poisoned cache entry — it removes the file and drops the key from the index (`Index.Remove`). **Shared store path**: `storeOneObject(storage, key, body, meta, audit) (status, err)` factors out the module-index peek-refuse (including the refusal counter + per-refusal log, which therefore fire for batch-put members too) + write_once + `PutStream` (audit + index append) logic so both `handlePutObject` (one object) and `handleBatchPut` (many) call it and cannot drift; it returns a `storeStatus*` (`stored`/`dropped`/`conflict`/`error`) the caller maps to an HTTP status (single PUT) or records per object (batch). `handlePutObject` maps `dropped`→200/no-store (module index), `conflict`→409, a wrapped `*http.MaxBytesError`→413
